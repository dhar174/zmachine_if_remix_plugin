# G2-D Editor authority

Issue #17 implements server-owned mode, scoped leases and exact approval for the #16 resolver. It preserves the #14–#16 wire schemas.

The coordinator authenticates the tool caller and checks its session scope before invoking `Authority`. Its methods accept verified owner identities. They are internal interfaces, not request handlers. Initialize or update the authoritative world and policy revisions via `setHead`. Restore uses a fresh generation, resets mode to Play and invalidates prior authority. A protection change invalidates Editor authority across the affected branch. Authorization state is outside the checkpoint. The in-memory implementation loses outstanding grants on process restart.

- The authenticated control handler accepts persistent `/play` and `/edit` and a request-scoped `/edit <instruction>`. It stores the latter with the verified request and expires it after five minutes or at terminal completion. The coordinator calls `finish` for cancellation and terminal failures outside preparation. An already-ended request cannot inherit persistent Editor mode. Ordinary Play and read-only inspection use `resolveWithoutGrant`.
- `prepare` uses the same resolver checks as execution and returns an opaque handle for the reviewed diff. The preview is a separate result without an executable plan. Preparing a replacement for a logical request invalidates its earlier candidate. The diff includes the previous facts, exact proposed operations and effects, policy lineage and the selected #15 compiler wrapper when applicable. The server hashes the same canonical JSON that it displays.
- A lease covers a registered remix presentation string assignment with one known, reversible write and no amendment. The server checks the complete derived footprint, explicit entity and field scope, policy revision, generation, authority epoch, expiry and three-use maximum. Every other Editor write needs exact approval. Verification does not consume a use.
- Mount `browserControl` with a verifier for the separately authenticated browser session. The handler displays the server-held diff and accepts approval only through a same-origin, CSRF-checked browser POST. The tool path can retrieve an existing reference for its exact head through `lookupApproval`. It cannot create one. Without a browser verifier the control surface returns `NEEDS_APPROVAL` with the compatibility reason. The loopback test injects a synthetic browser session. The private tunnel and scoped Auth0 deployment from #13 are the reference for #19 qualification.
- `resolveApproved` rechecks the grant or lease against the exact candidate, recomputes the reviewed diff, and passes verified authority into the existing resolver. `verifyApproval` checks server-held records without consuming them. The legacy `authorize` port checks identity, revision and mode and routes Editor writes to the richer resolver path.
- #18 must look up committed receipts before treating retries as new requests. Immediately before publication, it must reacquire the fresh world and authorization state, re-resolve the exact candidate and conditionally consume authority using the same request and head in its atomic publication unit. `consume` demonstrates conditional single use in memory. In-memory consumption alone does not provide durable crash recovery.

Run the focused authorization suite from `engine/` with `node --test tests/authorization.test.ts`. The tests cover A01, A11, A12, A33, A37 and A38 at the authorization boundary, browser HTTP loopback, and a real #15 selected subset. Live host and identity provider validation remain downstream.
