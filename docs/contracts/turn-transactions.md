# G2-E turn transactions

The application boundary is TurnService. The coordinator checks caller access to the owner/session/branch and supplies that verified scope separately from the validated #14 envelope. It supplies #15 compiler context only from trusted records. A preparation result is an immutable candidate preview, read-only inspection, or replay of a committed receipt. Inspection exposes only authorized, complete presentation reads from this fixture. Clarification and rejection publish no game state or provisional native output.

Same scoped request ID and same envelope return the saved receipt before head and approval checks. Same ID and different envelope or prepared proposal conflict. Candidate and approval references are server-held. A single logical request in flight joins the same execution. Separate requests can execute privately against one head, but only one can publish against that head. Retry guidance on transient aborts means look for a stored receipt first. An abandoned pre-publication request may re-execute on the same head. A transient abort can reuse an unexpired one-turn override. Cancellation and terminal failure end it. Editor authority revoked on coordinator restart must be re-established, and expired Editor candidates require a fresh logical request even after collection.

## Commit ordering

1. Claim the validated candidate and resolve it against the current head. Editor uses the #17 exact diff and current grant or lease. Release the database transaction before running the isolated executor.
2. Recreate the complete candidate, validate actual effects and postconditions, and verify the resulting checkpoint can be restored. Native fixture state includes RNG, output and pending input, with clocks, overlay, policy and lineage committed in the combined record. Amendments append unresolved clauses to the policy as non-executable records and retain the compiled amendment with all clause dispositions. There are at most 32 operations and 32 events, 64 KiB of output and facts, a 1 MiB checkpoint cap, and a 5-second cooperative execution deadline. The fixture is an in-process dependency and does not establish isolation from untrusted or uninterruptible adapters.
3. Commit the immutable, digest-addressed payload to the checkpoints table, still unreachable from the live head.
4. Start a short SQLite transaction. Recheck the request claim, candidate, head, policy revision, generation, capability plan and current authorization. Consume authority where required, update the authorization head, and publish the checkpoint reference, events, receipt and request outcome atomically. The receipt contains the existing #14 committed wire record plus rule/capability IDs and recovery guidance. No native output becomes visible from a rejected candidate. Native fixture operations consume the exact line or character text supplied in the validated envelope. Any future translation of natural-language input to a native command requires its own explicit contract and evidence. Editor edits cost zero time. An authored failed action can commit with measured time. The fixture also supports an overlay-only inventory transfer with a verified holder and both container updates.
5. Release the database transaction before responding. A crash after durable publication recovers the saved receipt without re-execution. A failure before publication leaves the previous head authoritative.

## Storage and scope

The local adapter uses Node's bundled SQLite, rollback journaling (DELETE), FULL synchronization, foreign keys and a 1-second busy timeout. Opening a database establishes a new coordinator token, fences the previous service from publication, clears abandoned claims and resets Editor authority outside game history. Run one active coordinator against a local database file. The fencing stops stale publication. Operations privately staged by an old process may already have run when the replacement starts. Concurrent service processes, shared disks, hard process isolation for untrusted executors, machine power-loss qualification, and production use are outside this fixture.

Abandoned checkpoint payloads can be collected when no active claim can publish them. Expired staging and expired authorization payloads can be removed. Committed history and request fingerprints are retained, along with override tombstones that prevent reusing ended request scopes. No application retention policy is imposed on historical receipts. The schema version is checked on open. Checkpoint IDs are unique across the database. Branch initialization with a reused ID returns VALIDATION_FAILED before creating any branch records. #18 creates a new local fixture store and defines no migration from probe artifacts or a previous database.

Mount the #17 browser handler with browserControl(service.browser, origin, verifyBrowser). This facade wraps each control action in the same store transaction used by the turn service. The per-request browser verifier and the tool principal remain separate. Run focused tests with node --test tests/turn-service.test.ts tests/authorization.test.ts from engine, followed by the schema suite, full engine checks and CI. The interruption cases kill a fixture child at acknowledged barriers and reopen the same database.

The activation checkpoint is the root of a fixture's published history. A restored head takes its parent from the selected save, and its receipt also records the displaced head. Recent history follows the selected ancestry. Exact historical turn receipts keep their original generation and request metadata.

A restore verifies the saved image outside the publication lock and stages its replacement checkpoint durably. Publication rechecks the current checkpoint, generation, both revisions, and exact approval. The head, lineage, authority reset, approval consumption, and restore result commit together.
